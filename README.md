# mtu-fragmentation-lab

MTU와 패킷 분할(fragmentation)이 API 성능에 미치는 영향을 검증한다.

## 배경

"MTU 1500이 기본이니까"라고 넘기지만:

- JSON 응답이 ~1460바이트(MTU 1500 - IP 20B - TCP 20B)를 넘으면 세그먼트 분할 발생
- 분할 지점을 넘는 순간 패킷 2개로 쪼개짐 → 1바이트 차이로 latency 변화
- VPN/터널링 환경에서 MTU가 1420~1460으로 줄어듦 → 예상치 못한 분할
- Jumbo Frame(9000) 환경이면 분할 없이 더 큰 응답 전송 가능

## 가설

| # | 가설 | 근거 |
|---|------|------|
| H1 | 응답 크기 1460B 전후에서 latency 불연속점이 존재할 것 | TCP 세그먼트 분할 경계 |
| H2 | MTU 1500 환경에서 1.5KB 응답이 1.4KB보다 측정 가능한 만큼 느릴 것 | 추가 패킷 1개 |
| H3 | VPN 터널(MTU 1420) 환경에서 1.4KB 응답도 분할될 것 | MTU 감소 |
| H4 | 10KB 응답에서 MTU 1500 vs 9000(Jumbo)의 throughput 차이가 존재할 것 | 패킷 수 7개 vs 2개 |

## 실험 설계

### 시나리오
- Go 서버에서 응답 크기를 파라미터로 조절: `GET /data?size=1400`
- 응답 크기: 100B / 500B / 1000B / 1400B / 1460B / 1500B / 2000B / 5000B / 10000B
- MTU 변경: `ip link set eth0 mtu 1500` / `1400` / `9000`

### 측정
- k6로 각 사이즈별 latency 곡선
- tcpdump로 실제 패킷 수 / 크기 확인
- iperf3로 MTU별 순수 네트워크 throughput 베이스라인 측정
